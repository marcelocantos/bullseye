# Test coverage gaps — 2026-04-12

Captured after fixing the root-level `targets.yaml` convergence bug
(commit `96d8a2f`). The fix shipped with unit tests for the two new
pure helpers, but the audit that produced this document identified
three integration gaps worth closing before the next release.

## Context

The bug I fixed was that `bullseye_convergence` reported
"hook not configured" for mnemo, despite mnemo having a perfectly good
`bullseye` rule in its `Makefile`. Root cause was twofold:

1. **`handle_convergence` computed the wrong `repo_root`** when
   `targets.yaml` lives at the repo root instead of under `docs/`.
   It stepped up two parent directories unconditionally, landing in
   the grandparent. No Makefile was found there, so the detection
   fell through to "no build file".

2. **`detect_invariants_command` pre-parsed the Makefile** by hand
   (`has_bullseye_rule`) to check whether a `bullseye` rule existed
   before invoking it. This duplicated logic that the build tool
   already implements authoritatively, and was brittle in several
   ways — tab vs space matters in Makefile parsing, `.PHONY:
   bullseye` is not a rule (the line count in `.PHONY:` was masking
   as the real rule in one earlier iteration of the check), and
   `include` directives are ignored. Even once (1) was fixed, (2)
   would keep producing false negatives whenever make's rule table
   disagreed with the pre-parse.

Both were fixed — (1) by factoring repo-root computation into a pure
helper `repo_root_from_targets_path` with explicit `docs/` detection,
and (2) by deleting the pre-parser and cascading from the build tool's
own stderr output via `stderr_indicates_missing_rule`. Unit tests
cover both helpers.

## Existing coverage

Unit tests added in `96d8a2f`:

- `handler::tests::repo_root_from_docs_targets_yaml` — conventional
  `<root>/docs/targets.yaml` layout.
- `handler::tests::repo_root_from_root_level_targets_yaml` — mnemo-
  style root-level layout. Regression guard for the original bug.
- `handler::tests::repo_root_from_nested_docs_like_dirname` — edge
  case where a `docs` directory exists for a reason other than the
  conventional layout.
- `convergence::tests::stderr_missing_rule_matches_gnu_make_output`
- `convergence::tests::stderr_missing_rule_matches_bsd_make_output`
- `convergence::tests::stderr_missing_rule_ignores_real_failures` —
  negative guard against classifying a normal build failure as
  "hook missing".

Existing integration tests that still pass unchanged:

- `convergence_end_to_end_green_invariants_picks_top_frontier`
- `convergence_end_to_end_red_invariants_blocks`
- `convergence_end_to_end_skip_invariants_flag_bypasses_hook`
- `convergence_missing_makefile_degrades_gracefully`
- `convergence_makefile_without_bullseye_rule_degrades_gracefully`
- `convergence_unreleased_fixes_detected_in_git_repo`

The last one is important: `convergence_makefile_without_bullseye_rule_degrades_gracefully`
now exercises the cascade path (run make → classify stderr → render
setup warning) rather than the pre-parse path. The test assertions
are identical, so the external contract is preserved.

## Gaps

### Gap 1 — Handler-level end-to-end test for root-level layout

**Severity**: high. This is the regression-guard that matters most
because it's the exact bug the user hit.

**What's missing**: every existing integration test in
`tests/core_test.rs` calls `bullseye::convergence::convergence(...)`
directly, passing `repo_root` explicitly as a function argument. They
entirely bypass `handle_convergence`, which is the layer that
contains the path-computation bug. None of the existing tests would
have caught the original bug, and none do now.

**What to add**: a test in `tests/core_test.rs` that drives
`bullseye::handle_convergence` (or whatever the public entry point
is) with a temp project laid out as:

```
tmp/
├── Makefile        # contains `bullseye:\n\t@true`
├── targets.yaml    # SIMPLE_TARGETS_YAML
└── .git/           # optional, for realism
```

…and asserts the output contains `Status: ✓ all green`. Mirror the
existing `convergence_end_to_end_green_invariants_picks_top_frontier`
test, just with the targets file at the root.

**Complication**: `handle_convergence` is currently a private `fn`
that returns `Result<CallToolResult, CallToolError>`. Options:

1. Make it `pub(crate)` or `pub`, and expose via a thin test helper
   that unwraps the `CallToolResult` to its text content.
2. Extract the path-aware setup into a small pure function (similar
   to `repo_root_from_targets_path`) that assembles the arguments
   for `convergence::convergence` and test that function.
3. Add a `test-support` module or `#[cfg(test)] pub fn` wrapper.

Option 2 is cleanest but may not catch every handler-level bug. Option
1 is the most pragmatic — expose `handle_convergence` to tests behind
a narrow API, add a test-only helper to extract the text from
`CallToolResult`, mirror the existing happy-path integration test.

### Gap 2 — mk stderr pattern unverified (RESOLVED)

**Status**: fixed and pinned by test on 2026-04-12.

**What was wrong**: `stderr_indicates_missing_rule` matched three
substrings: "no rule to make target" (GNU make, verified), "don't
know how to make" (BSD make, documented convention), and "no recipe
to make" — the last of which was annotated as "plan9 mk" but actually
guessed, and never verified. The `mk` in question is
marcelocantos/mk, not plan9port's `9 mk`. The real phrasing is
`mk: no rule to build "bullseye"` (see `graph.go:566`), so the
cascade would not have fired for a real user of `mk` with no
`bullseye` rule — they'd see "invariants failed" instead of "hook
not configured". Confirmed by running `mk nonexistent` against a
trivial `mkfile` and capturing stderr.

**Fix**: pattern updated to `"no rule to build"`, comments corrected
to reference marcelocantos/mk with a citation. New unit test
`stderr_missing_rule_matches_mk_output` pins the phrasing.

### Gap 3 — Mixed-layout precedence pinned by test

**Severity**: low. Not a known bug, just undocumented behaviour.

**What's missing**: a repo that has BOTH `docs/targets.yaml` AND a
root-level `targets.yaml` will be resolved by `store::discover` to
`docs/targets.yaml` (because the candidate list tries `docs/`
first). `handle_convergence` then feeds that path into
`repo_root_from_targets_path`, which detects the `docs` parent and
strips it, yielding the repo root. Correct behaviour, but
uncovered — nothing pins it.

**What to add**: a test in `handler::tests` that creates a temp
project with both files and asserts (a) `store::discover` returns
`docs/targets.yaml`, and (b) `repo_root_from_targets_path` resolves
to the repo root rather than `docs/`. Both assertions are one-liners;
the value is in catching a future change to either function that
accidentally inverts precedence.
