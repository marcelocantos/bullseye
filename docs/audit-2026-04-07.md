## Detailed findings

### Phase 1: Code quality

#### 1.1 Architecture and design

**Info** -- Clean architecture. The module layout (`schema`, `store`, `graph`, `ops`,
`handler`, `tools`, `render`) separates concerns well. Data flow is straightforward:
every tool call goes through discover -> load -> operate -> save+render. No circular
dependencies.

**Info** -- The `handler.rs` dispatch is a single match on `TargetTools` variants.
Each handler is a standalone function. This is idiomatic and easy to extend.

#### 1.2 Code correctness

**[3] High** -- `graph.rs:449-454`: `truncate()` slices by byte index (`&s[..max - 1]`),
which will panic if the slice boundary falls within a multi-byte UTF-8 character.
Target names containing non-ASCII characters (accented letters, CJK, emoji) will crash
the Mermaid graph renderer.
- **Fix**: Use `s.chars().take(max - 1).collect::<String>()` or
  `s.char_indices()` to find the correct byte boundary.

**[4] High** -- `store.rs:10-23`: `discover()` walks up from `start_dir` to the
filesystem root without any depth limit or boundary check. In an MCP server context,
the `cwd` parameter comes from an external client. A malicious or misconfigured client
could trigger scanning of the entire filesystem.
- **Fix**: Add a maximum traversal depth (e.g., 20 levels) or stop at common
  boundaries (home directory, git root). At minimum, document the behaviour.

**[15] Medium -- RESOLVED** -- `schema.rs:149-155`: `weight()` clamped the result
to `max(1.0)`, silently distorting ranking for very-low-value or very-high-cost targets.
- **Resolution**: WSJF ranking (`bullseye_rank`) has been removed from Bullseye.
  The `weight()` function and `parent` field are no longer part of the schema.
  Within a single repo, frontier-first scheduling replaces priority ranking.

**[18] Low** -- `handler.rs:70-71`: `CallToolError::unknown_tool` is used as a
catch-all error constructor for all error conditions (file not found, parse errors,
validation failures). Clients receiving this error type may misinterpret the cause.
- **Fix**: Use `CallToolError::new` with an appropriate error code, or introduce
  distinct error variants.

#### 1.3 Code hygiene

**[9] High** -- `cargo clippy` produces 13 warnings (7 collapsible-if, 4 redundant
closures, 1 derivable-impl, 1 default-constructed-unit-struct). `cargo fmt --check`
also fails with formatting divergences across multiple files.
- **Fix**: Run `cargo clippy --fix` and `cargo fmt`.

**[17] Low -- RESOLVED** -- `handler.rs:461`: `format_ranked` took an `indent`
parameter but every call site passed `0`.
- **Resolution**: `bullseye_rank` and `format_ranked` have been removed. This dead
  parameter no longer exists.

### Phase 2: Security

**[3] addressed above** -- The `truncate` panic is a crash vector reachable from
external input (target names are user-supplied).

**[4] addressed above** -- The filesystem traversal in `discover()` is the primary
security concern for an MCP server that receives `cwd` from external clients.

**Info** -- No secrets found in source code or git history. No `.env`, credential
files, private keys, or hardcoded tokens. The 16-commit history is clean.

**Info** -- No internal hostnames, private URLs, or PII found in any file.

**Info** -- No cryptographic operations in the codebase (not needed for this project).

### Phase 3: Testing

**Info** -- 44 tests, all passing. Good coverage of schema parsing, ranking, frontier
computation, rework cycles, tunnel detection, validation, rendering, and YAML roundtrip.

**Info** -- Tests are well-organised by feature, use a shared fixture, and make
meaningful assertions. No sleeps, no flakiness indicators.

**[16] Low** -- The test fixture (`tests/fixtures/docs/targets.yaml`) references
C++ concepts (spdlog macros, platform ifdefs, compilation units) which are unrelated
to this Rust project. This is cosmetically odd for an open-source repo -- readers may
be confused about the project's scope.
- **Fix**: Update fixture content to use Rust-relevant examples.

**Info** -- No tests for the MCP handler layer (tool dispatch, error formatting).
Acceptable for now since the handlers are thin wrappers, but worth noting for future
expansion.

### Phase 4: Performance

**Info** -- No performance concerns. The codebase processes small YAML files with
O(n) algorithms on the target count. The BFS in `tunnels()` is bounded by
`max_depth`. All operations complete in microseconds.

### Phase 6: Legal and licensing

**[1] Critical** -- The `LICENSE` file is a condensed summary, not the full
Apache 2.0 licence text. Apache 2.0 requires the complete licence terms to be
included. The current file is ~20 lines; the full Apache 2.0 licence is ~200 lines.
- **Fix**: Replace with the full Apache 2.0 text from
  https://www.apache.org/licenses/LICENSE-2.0.txt

**[2] Critical** -- `serde_yaml v0.9.34` is marked as deprecated by its maintainer
(David Tolnay). While this is primarily a dependency health issue, a deprecated
crate with no security maintenance is a licence/compliance concern for a new
open-source release -- adopters will flag it immediately.
- **Fix**: Migrate to an alternative YAML library. Options:
  - `serde_yml` (community fork)
  - `yaml-rust2` + manual serde integration
  - Consider whether JSON or a simpler format would suffice for the targets file.

**Info** -- All 110+ transitive dependencies are Apache-2.0, MIT, Apache-2.0 OR MIT,
Zlib, or Unlicense. All are compatible with Apache 2.0. No GPL, LGPL, MPL, or
copyleft dependencies.

**[12] Medium** -- No NOTICES or THIRD_PARTY file for dependency attribution.
Apache 2.0 and MIT licences require preservation of copyright notices in
redistributions. A binary distribution of bullseye should include attribution.
- **Fix**: Add a `NOTICES` file or generate one with `cargo-about`.

**[19] Low** -- The test file and Cargo.toml lack SPDX licence headers. All `src/`
files have them. Minor inconsistency.
